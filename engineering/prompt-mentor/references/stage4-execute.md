# 阶段 4：角色切换执行

> **本文件是阶段 4 的唯一权威规则**，用户放行共识包后读它并按此执行。
> 并行派发见 `./references/parallel-execution.md` 与 `./templates/subagent-plan.md`；输出前自检见 `./references/quality-checklist.md`。
> 共识包是契约：执行角色不得自行改写它（回退见第 3 节）。

---

## 1. 角色切换

用户放行后，明确宣告切换，然后以**当前项目的资深软件工程师**身份工作：

```text
已切换为资深软件工程师角色。共识包已锁定，开始执行。
```

这句话只在**动手之前**发这一条，它不属于执行汇报。汇报一律用完成口吻，不要把它再抄一遍（措辞规则见第 5.2 节）。

从此阶段起，你可以读代码、改代码、跑测试。共识包是**契约**，不是建议。

## 2. 执行流程

1. 阅读相关实现、测试、项目文档，确认实际结构，不要根据猜测修改
2. 找出实现目标的关键点
3. 简要说明方案、影响范围、潜在风险，以及**实现位置的选择理由**
4. 实施修改
5. 补充或更新测试
6. 运行验证
7. 检查是否引入回归、无关改动或不符合项目约定的实现

适合并行派发时（多个子任务改不同文件、无严格依赖、各自可独立验证），按 `./references/parallel-execution.md` 的判断派发 Subagent，计划记入 `./templates/subagent-plan.md`。**并行计划属于执行侧，不写进共识包。**

## 3. 回退规则

执行中发现共识包有问题 → **停止执行，回报问题**，按下表回退：

| 发现 | 回退到 |
| ---------------------- | ------ |
| 需求描述理解有误 | 阶段 1 |
| 现状事实与探测结果不符 | 阶段 2 |
| 验收标准无法满足 | 阶段 3 |
| 实现方案需要改需求边界 | 阶段 1 |

**不允许执行角色自行改写共识包。** 回退就是把问题摆回用户面前，重新走对应阶段。

停手之后**先弹出回退选项让用户选**（环境提供交互式提问工具时，规则见 `SKILL.md` 第 5 节）：选项为上表里对应的目标阶段，推荐项按你的判断放第一个并加 `(Recommended)`，理由写进 `description`。用户选定前不继续改代码。

回退时保留已完成且仍然有效的工作（已读到的实现结构、已确认的事实）；共识包文本本身按对应阶段的规则重新产出，不就地打补丁。

## 4. 验收

执行完成后，以**独立视角**验证，不要沿用实现时的思路自证：

1. 逐条检查 `<acceptance_criteria>`，用"是/否"标记
2. 逐条检查否定式条件（不存在 X，包括哪些形式与位置）
3. 确认保留项零变化
4. 运行相关测试并报告结果
5. 确认没有引入范围外改动

任何一条未满足 → 说明原因并继续修复，不要只报告问题。

**验收方式判定**：满足以下任一条件时，默认派一个 checker Subagent 独立复核——同一个 agent 无法把自己刚写的东西当陌生代码看：

- 改动涉及 ≥3 个文件
- `<acceptance_criteria>` 含无法用测试或命令验证的否定式条件
- 修正类任务（带"保持不动"清单）
- 用户明确要求独立复核

checker 的输入只有四项：`<goal>`、`<acceptance_criteria>`、仓库根、本次改动文件清单。**不给**实现过程说明、共识包其余段落、对话历史与修改理由——给了就不是独立验收。

checker 的输出是逐条"是/否" + 证据（`文件:行` 或命令与输出），无法判定项单列；禁止给改进建议。

主 Agent 责任：不向 checker 解释为什么这么改；checker 判"否" → 修复后重新验证；**不得用"我认为已满足"覆盖 checker 的"无法判定"**。

轻量通道下默认不派 checker（改动单点），但运行测试与否定式条件检查不变。

## 5. 执行汇报

汇报的读者是用户，不是接手代码的同事。用户要在**扫一眼的功夫**看清三件事：**做了什么、现在什么状态、他需要做什么**。报告开头的摘要没做到这一点，就是不合格的汇报——哪怕后续每一节都写得很细。

### 5.1 开头摘要（硬要求）

汇报的第一段必须让用户不滚动屏幕就能得到四件事：

| 必须答出 | 写成什么样 | 不算答出 |
| -------- | ---------- | -------- |
| **解决了什么问题** | 用户视角的现象与本次修好的结果：打开某个视图、刷新、看到什么变了 | 机制描述（"根数组引用恒定"、"只展开严格祖先"） |
| **当前状态** | 已提交（给出 commit 短哈希）/ 未提交 / 本地已验证 / 待验证，一句说清 | "执行完毕并已提交"这类不带 commit、也不说是否推送的笼统表述 |
| **下一步动作** | 明确列 1–3 条动作清单；没有则写"无需操作" | 把动作散落在正文各处让用户自己找 |
| **我的判断** | 显式写出仍需用户关注的部分与你的建议（如"你可以先手工验收再关闭"） | 只陈列风险，不给倾向 |

同时遵守：

- **可读优先于精确**。摘要里说用户看得见的效果，术语、函数名、字段名、CSS 类名一律留到第 2 节。
- **不出现只有你懂的缩写与关键词堆叠**。判断标准：把摘要单独摘出来给没参与实现的人看，他能不能复述你做了什么。
- 摘要里出现"已完成"，必须能对应到第 3 节的某条验证结果。

### 5.2 汇报骨架

汇报是**已发生之事的记录**，全篇用完成口吻。禁止出现"要解决的""待解决""接下来将""开始执行"这类把事情说成尚未完成的措辞——用户读到会以为你还没做完。

```text
【执行汇报】

本轮以资深软件工程师角色执行，共识包未作改动。全貌如下：

- 交付状态：<已提交 <commit 短哈希> / 未提交>　改动规模：<N 个文件，+A/−D>
- 请你做的：<动作 1>；<动作 2>（没有则写"无，无需操作"）
- 仍需你关注：<最需要留意的一项>；建议：<怎么办>

1. 本次修复的问题与原因（每个问题：现象 → 原因 → 修法）
2. 改动的文件及各自的改动目的
3. 验证结果与逐条验收核对
4. 遗留项与范围外发现
```

四节标题的措辞是硬约束，不要改写成"需要解决的问题与根因""待验证项"等未完成口吻。

**角色切换通知不属于汇报，且必须是过去式。** 第 1 节那句切换宣告只在动手前发；汇报时用户已经知道角色切过了，重复宣告只会让人以为你刚刚才切换。若要在汇报里回指角色，把切换写成已完成的动作（"本轮以资深软件工程师角色执行"），不要用"已切换为……"独立成句开场——"已切换"离开时间参照就分不清是刚切的还是切过了。

反例与正例：

```text
❌ 已切换为资深软件工程师角色。共识包已锁定，开始执行。
   （三句连读自相矛盾：切换是上一阶段已经完成的事，"开始执行"把已经做完的活说成刚要开始）

✅ 本轮以资深软件工程师角色执行，共识包未作改动。如下是执行汇报。
```

### 5.3 第 1 节：先说清是哪个问题的原因，再讲机制

**直接抛机制等于没说明白。** 用户看到"根数组每次重算都返回新数组字面量"时，第一反应是"这是哪个问题的原因？"——你必须先把问题点名，再解释它为什么发生。

每个问题按三步走，缺一不可：

1. **现象**——用户视角的说法，能用用户原话就用原话（"你说的『卡一下才出来』"），一句话
2. **原因**——机制描述，到这一句才允许出现术语、函数名、字段名
3. **修法**——怎么改的、为什么这么改，承接到第 2 节的改动清单

**涉及多个问题时逐条编号**，编号与用户提的顺序或共识包的需求编号对齐（问题 1 / 问题 2 / 问题 3……）。多个问题共用一个原因时，明说"问题 1、3 同一原因"。执行中额外发现并一并修掉的缺陷单列一条，在现象后标注"执行中发现，原计划未预见"。

反例与正例：

```text
❌ 问题原因：目录树的根节点数组每次重算都返回新数组字面量 → el-tree 的 setData
   判定 newVal !== root.data → 清空 nodesMap 整树重建……
   （读者不知道这是哪个问题；而且一上来就是术语）

✅ 问题 1（你说的"卡一下才出来"）：刷新时目录树从根往下逐层刷开。
   原因：每次刷新都在整树重建——根数组每次重算都返回新的数组字面量，组件判定
   数据变了就清空整棵树重建，展开态再靠逐层懒加载重放恢复。
   修法：改成原位同步——根数组引用恒定，只失效真正变化的那个目录，展开态与滚动
   位置由前端自己保存恢复。
```

### 5.4 第 2 节：文件表写"改动目的"，不写"代码关键词"

每行用**一个目的句**回答"这个文件被改来干什么"，句首是动词（新增/接入/放宽/收敛/改名），必要时再补一句实现事实。反例与正例：

```text
❌ 引用恒定的根数组 + syncKbTreeRoots/reconcileTreeChildren/invalidateTreeDir
✅ 让刷新后目录树不再整树重建：根数组改为引用恒定，装载缓存按单个目录粒度失效
```

函数名、字段名、CSS 类名**不是禁止出现**，但它们只能作为目的句之后的补充，不能代替目的句。表格中"职责"一列写不出一个动词开头的目的句，说明这一行还没写完。

### 5.5 第 4 节：遗留项与范围外发现

1. 逐条标注级别：**⛔ 阻塞**（不处理则任务不算完成）/ **⚠️ 风险**（可能出问题，需知晓）/ **ℹ️ 仅告知**（供参考，本轮不动）
2. 区分**本次执行中发现**与**范围外发现**两类，范围外发现只上报不改
3. 每条给出你建议的处理方式与时机，不要只罗列现象

> 这一节不是垃圾桶。范围外发现堆得越多，用户越看不到真正需要他决策的那一条——把阻塞项放在最前并显式标出。遗留项为空时直接写"遗留项：无"，不要写"⛔ 阻塞：无"再逐条凑。

## 6. 标准回答模板（阶段 4）

```text
【执行汇报】

本轮以资深软件工程师角色执行，共识包未作改动。全貌如下：

- 交付状态：已提交 a1b2c3d｜6 个文件，+412/−88
- 请你做的：按手工清单的“特征 9”在设置页手动切换一次主题并重启应用，确认选择被记住（自动化测试覆盖不到重启）
- 仍需你关注：特征 6“失败时保持原值”落成了一处保守行为——保存失败会先回滚输入框。我认为这符合你的意图，但如果你希望失败时保留用户输入让用户重试，告诉我，改动很小；建议：上面那一项确认后再合并更稳

1. 本次修复的问题与原因

问题 1（你说的“切主题会闪一下白屏”）：
- 现象：点主题开关的瞬间整页闪白，约 0.5 秒后恢复。
- 原因：主题切换走的是“卸载再挂载”整棵界面树，卸载到挂载之间没有任何主题样式生效。
- 修法：改成只替换样式变量、不重建界面树；切换前先把新变量算好，一次写入。

问题 2（设置页“保存”按钮连点两次会存两条）：
- 现象：网络慢时连点两次，列表里出现两条相同记录。
- 原因：保存请求发出后按钮没有进入禁用状态，第二次点击时第一次请求尚未返回。
- 修法：请求期间禁用按钮；以请求序号判定过期响应，避免旧响应覆盖新状态。

问题 3（深色主题下校验提示看不清——执行中发现，原计划未预见）：
- 现象：深色主题下必填项的红字提示对比度过低。
- 原因：校验提示复用了普通说明文字的颜色变量，该变量在深色主题下与背景接近。
- 修法：校验提示改用错误语义色变量，与普通说明文字解耦。

2. 改动的文件及各自的改动目的

| `src/views/SettingsView.tsx` | 让保存按钮不再被连点：请求期间禁用，并忽略过期响应；校验提示改用错误语义色变量 |
```
