# Subagent 并行组织

本文件管**要不要并行、怎么切分、怎么整合**。探测阶段与执行阶段共用同一套并行判据。

**分工：**

| 文件 | 管什么 |
|------|-------|
| 本文件 | 并行组织：决策树、切分结构、派发计划模板、整合责任 |
| `./references/subagent-recon.md` | 探测契约：探什么、边界约束、探查报告的输入与输出格式 |
| `./references/consensus-package.md` | 共识包段落结构与放行规则 |
| `./templates/subagent-plan.md` | 执行阶段派发计划的填写表格 |

**底线：`<parallelization>` 段落与派发计划只在阶段 4 的执行内部使用，不得写进共识包正文。** 共识包不含实现步骤与文件路径（见 `./references/consensus-package.md` 第四节）。

## 一、决策树

```
任务是否可以并行？
├── 包含多个子任务吗？
│   └── 否 → 不派发（单任务串行执行）
├── 子任务之间修改同一文件吗？
│   └── 是 → 不派发（先串行，或先合并设计）
├── 子任务之间有严格依赖吗？（B 需要 A 的产出）
│   └── 是 → 不派发（按依赖顺序串行）
├── 涉及全局一致性判断吗？（如统一命名、统一接口）
│   └── 是 → 不派发
├── 涉及不可逆操作吗？（数据库迁移、发布）
│   └── 是 → 不派发
├── 单个子任务工作量足够大吗？（≥ 半小时）
│   └── 否 → 不派发（派发开销 > 收益）
└── 全部通过 → 可以派发，建议 2-4 个 Subagent
```

**探测阶段的决策树**额外通过 `./references/stage2-probe-audit.md` 第 3 节的四维度（耗时 / 并发 / 上下文 / 复杂度）判断。全部落在"自己读"时，不要为了形式派 Subagent。

## 二、典型可并行结构

### 探测阶段

```
探测目标：某个界面对象的现状 + 它与其他对象的关系

├── Subagent A：主对象（有哪些功能项、各自作用对象与位置）
├── Subagent B：对照对象（同类对象的对应项，供对称性比对）
└── Subagent C：实现路径（某个功能的完整暴露位置与作用对象）
```

前提：A、B、C 探查范围互不重叠，输出格式按 `./references/subagent-recon.md` 的探查报告模板统一。总量控制在 2-4 个。

### 执行阶段：结构 1：按文件边界切分

```
主任务：新增外部 chat 接口
├── Subagent A：实现核心接口模块
├── Subagent B：实现会话管理接口模块
└── Subagent C：扩展设置页面（权限开关）
```

前提：A、B、C 涉及不同文件，无共享写入。

### 执行阶段：结构 2：按交付物切分

```
主任务：新增外部 chat 接口
├── Subagent A：实现代码（接口 + 业务逻辑）
├── Subagent B：更新文档（README + CLI）
└── Subagent C：编写测试（独立测试文件）
```

前提：测试文件、文档文件不与源码文件冲突。

### 执行阶段：结构 3：按角色切分（maker/checker 分离）

```
主任务：新增外部 chat 接口
├── Subagent A（maker）：实现代码
└── Subagent B（checker）：独立编写验证脚本
```

前提：B 在 A 完成后运行，但准备工作可并行。

## 三、派发计划模板

使用时机：阶段 4 执行角色判断"本任务适合并行"时，在执行内部建立派发计划。**该计划不写进共识包**，只在阶段 4 的执行汇报中体现。

```markdown
<parallelization>
本任务可拆分为以下可并行的子任务，建议派发给 Subagent 执行。

【Subagent A】[任务名]
- 输入：[具体的输入或前置条件]
- 输出：[具体的交付物]
- 涉及文件：[明确的文件列表或目录范围]
- 完成条件：[可验证的标准]
- 隔离边界：不得修改 [明确列出不碰的文件/目录]

【Subagent B】[任务名]
（同上结构）

【主 Agent 责任】
- 派发任务，定义各 Subagent 的输入输出契约
- 处理共享部分（如公共类型定义、配置键名约定）
- 整合各 Subagent 产出
- 执行最终验收（见 acceptance_criteria）
- 冲突解决：若发现两个 Subagent 修改同一文件，立即停止并串行处理

【并行前提】
- 各 Subagent 不得修改同一文件
- 各 Subagent 的输出格式需提前约定（避免整合时格式不一）
- 涉及共享依赖（如公共类型、配置结构），主 Agent 先完成共享部分再派发
- 如果并行过程中发现依赖冲突，可以降级为串行，不要强行并行

【推荐的 Subagent 数量】
2-4 个。超过 4 个时，整合成本通常大于收益。
</parallelization>
```

## 四、关键约束

1. **派发是优化，不是必需**：不要默认要求派发，只有符合并行条件时才建议。
2. **保守优先**：不确定时串行。并行的失败成本（文件冲突、整合困难）远大于串行的时间成本。
3. **数量控制**：推荐 2-4 个 Subagent。超过 4 个时，整合成本会超过并行收益。
4. **契约先行**：派发前，主 Agent 必须先完成共享部分（公共类型、字段名约定、配置结构、输出格式模板）。
5. **主 Agent 保留整合责任**：派发不是甩锅。主 Agent 必须整合产出、处理冲突、执行最终验收。
6. **探测阶段另有一条**：信息够了就立即停止，不要为了把计划里的 Subagent 用完而继续探。

## 五、反模式

- ❌ 任务可以并行但强行串行（浪费效率）
- ❌ 任务不能并行但强行并行（制造冲突）
- ❌ 用 Subagent 去做需要全局一致性判断的事
- ❌ 让两个 Subagent 修改同一文件
- ❌ 派发的 Subagent 数量超过必要（超过 4 个）
- ❌ 派发前没有定义输出契约（导致整合返工）
- ❌ 主 Agent 把整合责任推给 Subagent
- ❌ 把派发计划（`<parallelization>` 段落）写进共识包
- ❌ 探测阶段派 Subagent 去探查范围重叠的对象（产出重复，还得自己去重）

## 六、判断示例

### 例 1：探测阶段，适合并行

```
任务：拆开多选右键菜单里被合并的两个入口

判断：
- 有多个独立对象可并行探 ✓（主对象 + 对照对象 + 某个功能的实现路径）
- 产出代码量大，会稀释后续上下文 ✓
- 多步操作（定位 → 比对 → 归类 → 标记）✓

结论：派 3 个 Subagent（主对象 / 对照对象 / 实现路径）
```

### 例 2：探测阶段，自己读就够

```
任务：确认某个菜单项是否存在

判断：
- 只需读 1-2 个文件 ✓（落在"自己读"）
- 单一对象，无对照 ✓
- 单步核实 ✓

结论：AI 自己读，不派 Subagent
```

### 例 3：执行阶段，适合并行

```
任务：新增外部 chat 接口 + 更新文档 + 补充测试

判断：
- 子任务 A（接口实现）、B（文档）、C（测试）修改不同文件 ✓
- 无严格依赖（测试可以基于已有接口写） ✓
- 每个子任务工作量足够大 ✓
- 无不可逆操作 ✓

结论：建议 3 个 Subagent 并行
```

### 例 4：执行阶段，不适合并行

```
任务：重构全局命名规范（涉及 30 个文件）

判断：
- 需要全局一致性判断 ✓（不通过）
- 修改大量共享的接口定义 ✓（不通过）

结论：不派发，单 Agent 串行处理
```

### 例 5：执行阶段，部分适合

```
任务：新增外部 chat 接口（含 schema 迁移）

判断：
- schema 迁移不可逆 ✗
- 接口实现可以并行 ✓
- 但接口依赖 schema 定稿 ✗

结论：主 Agent 先完成 schema 迁移，再派发接口实现
```

## 七、与 maker/checker 分离的关系

派发 Subagent 与 maker/checker 分离是**两个独立的机制**：

- **派发**：解决"多个独立任务并行"的问题
- **maker/checker**：解决"同一个任务需要验证"的问题

两者可以同时使用：

```
主任务
├── Subagent A（maker）：实现接口
├── Subagent B（maker）：更新文档
└── Subagent C（checker）：验证 A 和 B 的产出
```

但如果任务很小，两者都不需要。阶段 4 的验收要求以独立视角逐条核对，其 checker 派发条件、输入边界与输出格式见 `./references/stage4-execute.md` 第 4 节——**checker 就是 maker/checker 分离在验收环节的具体形态**：输入只给 `<goal>` + `<acceptance_criteria>` + 仓库 + 改动清单，不给实现过程与修改理由。
