# 阶段 1：需求澄清

> **本文件是阶段 1 的唯一权威规则**，进入阶段 1 前完整读一遍。
> 本阶段锁定的两个产物，在用户锁定后原文写入阶段 3 共识包的 `<optimized_requirement>` 与 `<requirement_list>`。
> 相关文件：`./references/optimized-requirement.md`（需求描述怎么写）、`./references/requirements-by-type.md`（分类型追问清单）、`./references/prompt-count-decision.md`（任务数量与多份共识包）、`./references/quality-checklist.md`（输出前自检）。

---

## 1. 目的与输入

**目的**：把用户模糊的需求，转成可确认、可验收、原子化的需求描述与清单，让用户在探测之前锁定意图。

**输入**：用户原始需求 + AI 已读的项目说明文档（agents.md / README / docs）。

覆盖以下类型的需求：新功能、Bug 修复、性能优化、重构、UI 或交互调整、测试补充、文档改进、架构调整、部署或工程问题、代码解释。先判断用户真正想要的结果，而不是直接改写用户原话。

### 2. 两个产物，同时给

每轮回复同时输出这两个东西：

**① 【优化后的需求描述】（放在回复最前面）

叙述性文本，把用户原话里的模糊指代、模糊范围、不可验证动作改写成精确版。用户第一眼看到的就是自己那句话被改写后的样子——教学就发生在这里。写法见 `./references/optimized-requirement.md`。

**② 【需求清单】

原子化的功能项列表，每条是一个**用户可感知的功能**，独立编号。不得把相邻功能写成一条。

### 3. 需求信息模型

尽量补全以下信息：

| 信息 | 说明 |
|------|------|
| Goal | 最终要达成的目标（可验证的完成标准） |
| Current State | 当前发生了什么 |
| Desired State | 用户期望看到什么 |
| Scope | 哪些范围需要处理 |
| Non-goals | 明确不处理什么 |
| Evidence | 报错、日志、截图、复现步骤等证据 |
| Constraints | 技术、兼容性、时间、性能或业务限制 |
| Acceptance Criteria | 如何判断任务完成（Done when...） |
| Validation | 需要运行哪些测试、检查或验证 |
| Risk | 可能影响哪些已有行为 |

不要求用户一次性提供全部信息。根据任务类型，优先询问最能影响方案的问题。

**分任务类型的具体追问清单**，见 `./references/requirements-by-type.md`。

### 4. 阶段 1 的硬约束

**需求清单必须原子化。** 每个用户可感知的功能独立成条：

- 不得把多个功能合并成一条：`设置 0–5 星、设置／清除颜色标记`
- 不得因为两个功能在 UI 上挨着就写成一个入口
- 不得把"功能 A + 功能 B"写成一个菜单项、一个面板或一次交互

不确定是否该合并时，**列为待确认问题**，不要自行合并。

**"复用 X"必须转成防分叉条款。** 用户说"复用 X""沿用 X""和 X 一样""直接照搬 X""走 X 那一套"时，不得照原话写进需求描述。必须翻译成可验证的防分叉条款，包含四件事：

1. **复用同一实现**：点名要复用的是哪部分能力或逻辑
2. **禁止平行副本**：不得复制一份再改
3. **允许的最小适配范围**：如果当前实现与单个对象耦合，允许做哪些参数化适配
4. **回归条件**：适配后原调用方的行为与外观零变化

```text
用户原话：“收藏星级直接复用单选菜单那一套”

❌ 照原话写：收藏星级复用单选菜单的实现
   → 执行者最省事的路径是复制一份单选星级改一改，表面一致、代码分叉

✅ 精确条款：
   - 复用单选菜单已有的星级能力与逻辑，必须是同一份实现（非复制分叉）
   - 不得新建平行组件／平行函数／平行样式
   - 若当前实现与单个文件耦合，允许做最小参数化适配使其作用于文件列表
   - 适配后单选菜单的星级行为与外观零变化（回归条件）
```

**AI 自己发明的产品决定不得混进需求描述。** 分组方式、条目顺序、交互形式、默认值、**把多个功能合并成一个入口**、命名措辞、边界情况处理策略——不得作为既定需求呈现，也不得混进【优化后的需求描述】。这些决定只有两个去处：**列为待确认项**（单列进【需要确认】，逐条编号，由用户逐项裁决），或**留给执行阶段**。

用户拒绝某条待确认项后，修订版必须**真正移除**该条，不得改写成其他形式保留。

### 5. 追问规则与阶段 1 的异常处理

**追问的触发条件是"判断现有信息不足"，不是流程位置。** 只有当你判断"缺这个信息就没法定需求 / 没法写验收 / 没法交给用户裁决"时才追问；信息已经足够就不问。它主要出现在两处：阶段 1 需求尚未锁定时，阶段 2 分流需要核对或交用户裁决时。

提问思路：**结构化、层层递进**——一轮只推进一层，先问完能定方案的问题，再判断是否需要下一轮；问到"方案能定、验收能写"为止，不为问完而问。这是本 Skill 自己的提问方式，不依赖任何外部 Skill。

底线：

1. 只问影响任务理解、实现范围或验收结果的问题
2. 每轮 3–5 问
3. 不为了形式完整而问用户无法判断的技术细节
4. 不重复问已从文档、代码或用户描述中得到的信息
5. 非关键未知信息，标记为"由执行阶段核实"，不要拦在这里

阶段 1 的异常处理：

| 情况 | 处理 |
|------|------|
| 用户说"按你的理解生成" | 视为允许带明确假设继续，但假设必须显式标注 |
| 描述里有多个互相冲突的目标 | 必须先让用户确定优先级，不能带着冲突进阶段 2 |
| 用户只说"优化一下""修复一下" | 至少确认优化对象、期望结果、完成标准 |

优先用选择题或短问题降低用户表达成本：

```text
为了锁定需求，还需要确认三点：

1. 这次优化优先解决什么？
   A. 性能
   B. 可维护性
   C. 用户体验
   D. 其他

2. 是否允许改变现有 API 或数据结构？
3. 什么结果可以视为完成？
```

### 6. 需求锁定门槛

用户锁定需求之前，不要进入阶段 2 的探测派发，也不要输出共识包。

锁定标志：用户明确回复"确认""就这样""按这个来"，或逐项修改后表示没有其他问题。

**语义改写必须显式标记**：凡对用户原话做了语义改动（收窄 / 扩大 / 合并 / 拆分 / 新增约束 / 改变范围）的条目，在【需求清单】中标注 `⚠ 已改写`，并在锁定前单独列出"我改了什么、为什么"；纯措辞润色不标注。存在 `⚠ 已改写` 条目而用户尚未对其表态时 → **不算锁定**（用户可以一次回复统一认可）。

**轻量通道下的差异**（判据见 `SKILL.md` 第 4.2 节）：省略完整的【项目文档摘要】，只写 1–2 行结论；允许在同一轮回复中同时给出【需求清单】与简版共识包，用户回"确认，开始"即同时完成锁定与放行。原子化要求与防分叉条款不变。

锁定后，把【优化后的需求描述】与【需求清单】作为阶段 3 共识包的 `<optimized_requirement>` 与 `<requirement_list>` 原文写入。

### 7. 任务数量识别

在展示需求清单时，同步说明识别到的任务数量。

**判断规则**：

- 用户表达里的并列连词（"另外""还有""顺便""同时"）→ 多个任务
- 用户表达里的多个独立动词且目标不同 → 多个任务
- 用户表达的多个内容共享同一个目标 → 一个任务（用批次解决，不拆分）
- 无法判断 → 在追问中确认

**关键区分**：数量由"用户意图的边界"决定，不由"任务复杂度"决定。用户说"重构整个前端，包括路由、状态管理、组件库、样式"，表达的是**一个目标**——1 份共识包，用批次解决。用户说"新增接口，另外优化界面"，表达的是**两个目标**——2 份共识包。

识别为多个任务时，在需求清单后写明：

```text
识别到的任务数：2 个（建议拆成 2 份共识包）
拆分理由：两个任务边界清晰，无共享改动面，可独立验证
```

用户可以在锁定前否决拆分。详细规则和总览模板见 `./references/prompt-count-decision.md`。

### 8. 标准回答模板（阶段 1）

```text
【优化后的需求描述】
你的原始描述：
> [用户原话]

优化后的需求描述：
> [叙述性精确版]
>
> **需要确认**：[仍不确定、会影响方案的点]

【需求清单】
1. [原子化功能项]
2. [原子化功能项]

【项目文档摘要】
已读取：[文档路径]
项目概况：[仅根据文档得出的简短总结]
尚未确认：[不能从文档得出的内容]

【需要确认】
1. [问题]
2. [问题]
3. [问题]

其中我自己的产品决定单独列出（这是我的决定，不是你的需求，请逐项裁决；未裁决的留给执行阶段）：
- D1. [分组方式 / 交互形式 / 默认值 / 合并方案 / 命名措辞 / 边界情况策略]

【任务数】识别到 N 个任务（N>1 时说明拆分理由与建议执行顺序）

暂不进入探测与执行。待需求锁定后，我会核实现状并生成共识包。
```

### 9. 无法读取项目文档时

```text
【项目文档状态】
未找到或无法读取允许的项目说明文档：[说明情况]

我仍会继续：先澄清需求，再通过读取代码或派 Subagent 探测核实现状。
请提供以下信息中你方便给出的部分：
- 项目用途
- 技术栈或运行环境
- 当前任务
- 期望结果
- 约束和验收标准

确实无法核实的部分，会作为未核实假设写进共识包，由执行阶段确认。
```
