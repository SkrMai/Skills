# 阶段 2：探测与审计

> **本文件是阶段 2 的唯一权威规则**，进入阶段 2 前完整读一遍。
> 探测契约的输入 / 输出模板见 `./references/subagent-recon.md`；重设计类的三查细则与裁决表见 `./references/redesign-audit.md`；并行组织见 `./references/parallel-execution.md`。
> 本阶段只产出事实与待裁决项，不生成共识包、不改项目。

---

## 1. 目的与权限

**目的**：核实需求描述中的现状假设是否属实；涉及已有对象时做合理性审计，找出"预存的不合理"。

两层决策：**层一 是否需要探测**、**层二 探测由谁执行**。发起探测、决定探测范围、决定是否审计——**权限均归 AI**，用户不介入发起环节，但派发前要告知（第 4 节）。

用户只在两个点介入：审计发现"需求之外的不合理"→ 用户裁决；审计发现"与用户需求冲突"→ 回阶段 1。

### 2. 层一：是否需要探测？

三个必要条件（**全过则跳过探测**，直接进入阶段 3）：

1. 需求描述中所有现状假设均已核实（来自已读文档 / 用户确认 / 上下文已经实际探查过）
2. 任务不涉及对已有对象的重新设计
3. 无对照对象需要比对

任一不满足 → 需要探测。

**反向兜底**：探测中若发现信息已足够，立即停止，不为了探而探。范围以"能支撑判据"为限，不做全项目扫描。

### 3. 层二：探测由谁执行？

四个维度，任一命中"触发 Subagent"即发起 Subagent：

| 维度 | 触发 Subagent | 倾向 AI 自己读 |
| ------ | ------------------------------- | --------------- |
| 耗时 | 读取量大（多文件 / 多模块），单线程读完耗时明显 | 只需 1–2 个文件即可核实 |
| 并发 | 有多个独立对象可并行探（主对象 + 对照对象、多个变体） | 单一对象，无并行空间 |
| 上下文 | 探测产出的代码量大，会稀释主对话后续上下文 | 产出量小，读进来不影响后续 |
| 任务复杂度 | 探测本身是多步操作（定位 → 比对 → 归类 → 标记） | 单步核实（确认某入口是否存在） |
| 待查事实数量 | 需核实 3 条以上相互独立的事实 | 只需 1–2 条，且用户在对话中可直接回答 |

判定规则：

- 任一命中"触发 Subagent"列 → 发起 Subagent
- 四个维度全部落在"倾向自己读"列 → AI 自己读
- 边界模糊 → **倾向自己读**（Subagent 有调度成本，宁轻勿重）
- 待查事实 ≤2 条，且属于**用户在界面上能直接观察到的事实**（入口位置、当前行为、哪种选择状态可用）→ 在阶段 1 的追问里一次问清，不为此派 Subagent。问的是一眼可见的事实，不是让用户读代码抄清单
- Subagent 总数控制在 2–4 个，超过则整合成本大于收益
- 探测中发现信息已足够，**立即停止**，不要凑满计划数量

**并行发起**：主对象 + 对照对象 → 各一个 Subagent，可并行；多个变体（单选 / 多选；文件 / 文件夹）→ 可拆多个 Subagent。

### 4. 探测前告知用户

探测前用一句话说明，让用户可以打断：

```text
我要探测 <对象> 的现状，重点确认 <要点>。预计 N 个 Subagent：<A/B/C>。
（或：我自己读 N 个文件，不派 Subagent）
```

用户喊停就停下核对方向。**这是告知，不是征询**——AI 自己决定探测与否、派谁去；告知只是把决定暴露出来，避免探测方向跑偏后才发现。

### 5. Subagent 探查契约

探查 Subagent 只做事实收集，不做设计判断。完整契约（输入模板、输出模板、边界约束、导师接法、盲区处理）见 `./references/subagent-recon.md`。

要点：

- **输入**：对象 / 位置线索 / 变体 / 对照对象 / 探查范围
- **边界**：禁止提出改进建议、禁止判断功能该不该在这里、禁止合并或归类功能项、禁止给出实现方案；发现可疑项只标记，不裁决
- **输出**：功能项清单（名称 / 作用对象 / 出现位置 / 证据）、对称性对照、可疑项标记、探查范围与盲区

### 6. 审计

**是否需要审计，由 AI 判断**。指引性判据：

| 情况 | 倾向 |
|------|------|
| 重设计类任务 | 通常需要 |
| 涉及对称性 / 归属 / 冲突可能 | 通常需要 |
| 纯新增功能 | 通常不需要 |
| 探测报告已直接回答需求问题 | 不需要 |

三查：

| 查什么 | 动作 | 产出 |
| ------ | -------------------------------- | ------------ |
| 对称性 | 同类对象间哪些项一边有一边没有 | 不对称项清单 |
| 归属 | 作用对象与所在层级是否匹配 | 错配项清单 |
| 冲突 | 新功能与现有项是否重复或语义重叠 | 重叠项清单 |

三查清单、裁决表模板与验收标准写法见 `./references/redesign-audit.md`。

**审计产出是待裁决项，不是结论。** 不得默认保留，不得自行决定移除或合并。

### 7. 分流

```text
探测 + 审计完成
│
├── 与用户需求冲突（用户要的 X 不存在 / 用户描述的现状有误）
│   → 停止，向用户核对 → 回阶段 1 重新出需求描述与清单
│
├── 需求之外的不合理（对称性 / 归属问题，与本次需求无关）
│   → 向用户裁决：一并处理 / 保留不动 / 待定
│   → 裁决结果进阶段 3
│
├── 信息已足够（探了发现不需要探）
│   → 立即停止，进入阶段 3
│
└── 无异议
    → 进入阶段 3
```

分流走到"回阶段 1"或需要用户裁决时，**先判断是不是真的信息不足**：不足才追问（见 `./references/stage1-clarify.md` 第 5 节），足够就直接进阶段 3，不要为了走完流程再问一轮。

把探测结果如实摆给用户，不要为了让流程顺畅而略过。

### 8. 输出与异常处理

阶段 2 的输出四类：

- 已核实事实（来自探测，标注来源）
- 待核实项（来自文档 / 口述，标注"由执行阶段核实"）
- 审计待裁决项
- 盲区

异常处理：

| 情况 | 处理 |
|------|------|
| 探测发现信息不足，需要再探 | 可再发起，但 Subagent 总数仍控制在 2–4 个 |
| Subagent 产出与需求无关 | 中止该 Subagent，改自己读 |
| 探测中发现用户描述与文档冲突 | 走"与需求冲突"分支，停止并核对，回阶段 1 |

### 9. 标准回答模板（阶段 2）

```text
【优化后的需求描述（已锁定）】
[1–2 行摘要；有微调时输出更新版并标注微调处]

【探测发起】
我要探测 <对象> 的现状，重点确认 <要点>。预计 N 个 Subagent：<A/B/C>。

【探查报告】（Subagent 返回汇总）
| # | 功能项 | 作用对象 | 出现位置 | 证据 |
[每个探测对象一张表；附与对照对象的逐项比对]

【现状审计】
- 对称性查：[不对称项]
- 归属查：[错配项]
- 冲突查：[重叠项]

【需要你裁决】
T1. [待裁决项]：现状是……；可选处置：一并处理 / 保留不动 / 待定
```

探测后无异议、审计无待裁决项时，直接进入阶段 3，省略裁决段落。
