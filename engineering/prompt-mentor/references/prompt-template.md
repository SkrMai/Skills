## 默认生成模板

用户确认后，默认生成以下结构的提示词。根据任务类型可删除无关部分，但不要删除目标、约束、验收标准和验证方式。

```text
你是当前项目中的资深软件工程师。请先理解现有实现，再完成下面的任务。

<goal>
[用一句话说明最终目标，必须是可验证的完成标准]
</goal>

<project_context>
[只放与本任务相关的项目背景]
[注明来源]
[注明需要由你检查确认的内容]
</project_context>

<task>
[明确描述需要完成的工作]
</task>

<current_state>
[当前行为、问题、错误或已知现象]
</current_state>

<scope>
必须处理：
- [范围 1]
- [范围 2]

不在本次任务范围内：
- [非目标 1]
- [非目标 2]
</scope>

<constraints>
- [兼容性要求]
- [不能改变的现有行为]
- [性能或安全要求]
- [依赖和技术限制]
</constraints>

<acceptance_criteria>
完成必须满足（Done when）：
- [ ] [可验证标准 1]
- [ ] [可验证标准 2]
- [ ] [边界情况标准]
</acceptance_criteria>

<verification>
任务完成后，请以独立视角验证结果：
1. 逐条检查 acceptance_criteria 是否全部满足
2. 运行相关测试并报告结果
3. 确认没有引入范围外的改动
如果任何一条验收标准未满足，请说明原因并继续修复。
</verification>

<current_state_inventory>
[仅重设计类任务。要求执行者先盘点现有功能项清单、对照同类对象、判断作用域是否匹配，
并以上报形式给出，再开始修改。模板见 ./redesign-audit.md 第六节]
</current_state_inventory>

<audit_findings_required>
[仅重设计类任务。要求执行者把盘点中发现的不合理逐条上报，
在确认前不得自行决定移除或保留，不得顺手合并功能项。模板见 ./redesign-audit.md 第六节]
</audit_findings_required>

<corrections>
[仅修正类任务。逐条列出“当前行为 → 期望行为”。完整模板见第二节]
</corrections>

<do_not_touch>
[仅修正类任务。显式列出已实现且无问题的部分，禁止本次改动、禁止顺手重构。
完整模板见第二节]
</do_not_touch>

<workflow>
1. 先阅读与任务相关的实现、测试和项目文档，确认实际结构，不要根据猜测修改。
2. 找出导致当前问题或实现目标的关键原因。
3. 简要说明你的方案、影响范围和潜在风险。
4. 按方案实施修改。
5. 补充或更新必要的测试。
6. 运行与本次修改相关的验证。
7. 检查是否引入回归、无关改动或不符合项目约定的实现。
</workflow>

<uncertainties>
[列出已知但尚未确认的事项]
如果这些事项会影响实现，请先检查仓库或提出具体问题，不要自行编造事实。
</uncertainties>

<response_contract>
完成后按以下顺序汇报：
1. 问题原因或实现思路
2. 修改的文件及每个文件的作用
3. 测试或验证命令及结果
4. 未解决的问题、风险或后续建议

如果需求存在无法安全推断的关键内容，请先提出问题，不要直接采取高风险方案。
</response_contract>
```

## 修正类任务模板

用于**已经实现并交付、但有具体问题需要定点修正**的功能。不要用默认模板改写需求描述，直接用本结构。

核心是三段结构：**修正项 / 保持不动 / 否定式完成条件**。缺少任何一段，执行 Agent 都容易借小修做大改。

```text
你是当前项目中的资深软件工程师。下面是对一个已交付功能的定点修正，不是重做。

<goal>
修正 <功能名> 的 <具体问题>，其余已实现部分保持零改动。
</goal>

<context>
- 该功能已经实现并交付
- 本次是定点修正，不是重构，也不是重新设计
- 前置依赖：[无 / 上一份提示词的产出]
</context>

<corrections>
逐条列出要改什么，每条写清“当前行为 → 期望行为”：
1. <修正项 1>：当前 <现状>，期望 <期望结果>
2. <修正项 2>：当前 <现状>，期望 <期望结果>
</corrections>

<do_not_touch>
以下部分是已实现且无问题的，本次不得改动，也不得顺手重构、重命名、格式化：
- <保持不动的部分 1>
- <保持不动的部分 2>

禁止修复本清单之外的任何问题。发现其他问题只上报，不修改。
</do_not_touch>

<constraints>
- 不扩大修改范围（原因：修改范围越大，回归风险越高）
- [其他约束]
</constraints>

<acceptance_criteria>
修正项完成（Done when）：
- [ ] <修正项 1 的可验证结果>
- [ ] <修正项 2 的可验证结果>

不应存在（逐项枚举位置与形式）：
- [ ] <对象> 中不存在 <不应存在的功能>，包括：<位置 1>、<位置 2>、<形式 1>

保持不动：
- [ ] <do_not_touch 清单> 中的功能行为与外观零变化
</acceptance_criteria>

<verification>
只验证以下三项，不要扩大验证范围：
1. 逐条对照 <corrections>，用“是/否”标记每条是否满足
2. 逐条对照 <acceptance_criteria> 的否定式条件
3. 确认 <do_not_touch> 清单中的功能未被改动
如果任何一条未满足，说明原因并继续修复；发现清单外的问题只上报，不要自行修改。
</verification>

<response_contract>
完成后按以下顺序汇报：
1. 每条修正项的改动说明
2. 修改的文件及每个文件的作用
3. 否定式条件的逐条核对结果
4. 确认 <do_not_touch> 清单未被触碰
5. 未解决的问题、风险或发现的范围外问题（只上报，不修改）
</response_contract>
```

**使用要点：**

- `do_not_touch` 清单必须显式写出功能名，不要用“其他功能”这种笼统表述
- 否定式条件必须枚举位置与形式（菜单项 / 子菜单 / 面板区块 / 设置项），只否定一种形式会留下“换个形式加回来”的口子
- 不要在修正类提示词中加入“顺便优化”“如发现问题一并修复”这类开口条款

## 框架选用决策树

```text
用户需求 →
├── 有明确的“做完标志”（测试通过/错误消失/指标达标）？
│   → 用 Goal Contract（见下方）
├── 需要定义角色和输出格式，且任务较复杂？
│   → 用完整模板 + Goal Contract 的验收标准
├── 只是解释/咨询/对比？
│   → 用简化模板（角色 + 任务 + 上下文 + 输出格式）
└── 不确定？
    → 默认用完整模板（可验证性优先）
```

## 各框架详解

### Goal Contract（核心框架）

Goal Engineering 的核心洞察是：大多数 agent 会话在“模型听起来做完了”时就结束了，但测试可能失败、迁移可能未完成。可验证的停止条件解决了两个问题——agent 太快放弃，或 agent 无限循环做无方向的修改。

**结构：**

```markdown
【目标】
（一句话描述最终状态，必须可验证）

【当前状态】
（描述现状，包含已知的失败现象或差距）

【完成条件】（Done when）
- [ ] 条件1
- [ ] 条件2

【约束】
（绝对不能做的事 + 原因）

【方法建议】
（可选，给执行者提供思路但不强制）
```

**示例：**

用户原始需求：“登录接口有时候报错，帮我修一下。”

```text
【目标】
修复登录接口的空指针异常，确保所有合法请求返回200，非法请求返回明确的错误码。

【当前状态】
登录接口在部分请求下返回500，日志显示 NullPointerException 发生在 UserService.authenticate()。

【完成条件】（Done when）
- [ ] 所有合法登录请求返回200 + 用户信息
- [ ] 空参数请求返回400 + 错误提示
- [ ] 新增3个以上边界情况的单元测试且全部通过
- [ ] 已有测试无回归

【约束】
- 不修改数据库表结构（原因：生产环境迁移成本高）
- 不改变现有 API 响应格式（原因：前端已依赖当前格式）
- 保持登录 token 生成逻辑不变
```

### 验证者指令（Maker/Checker 分离）

对于复杂任务，在提示词中加入验证者角色。Goal Engineering 的 maker/checker 分离模式正是为了解决“看起来做完了”与“实际做完了”之间的差距。

```text
<verification>
完成实现后，请切换为验证者视角，独立检查：
1. 逐条对照 acceptance_criteria，用“是/否”标记每条是否满足
2. 运行所有相关测试，报告通过/失败数量和具体失败原因
3. 检查是否引入了非目标范围内的改动
4. 如果任何条件未满足，说明原因并继续修复，不要仅报告问题
</verification>
```

### STCO 框架（适合新功能）

| 要素 | 含义 |
|------|------|
| Situation | 背景和角色 |
| Task | 具体任务（可衡量的输出） |
| Constraints | 边界和格式要求 |
| Output | 期望的结构和质量标准 |

STCO 的优势在于四要素互不重叠，适合需要明确定义角色和输出格式的场景。

### 轻量场景（代码解释/咨询）

适合不需要执行-验证循环的场景，使用简化模板：

```text
【角色】
你是一位[具体角色]，擅长[具体能力]。

【任务】
[明确描述需要完成的任务]

【上下文】
[只放与本任务相关的背景信息]

【输出格式】
[期望的输出结构]
```

## 写作规范细则

1. **明确具体**：用直接动作动词开头（“分析”“生成”“重构”）
2. **正向指导**：告诉 AI“要做什么”，而非“不要做什么”。正向指令的合规率更高
3. **提供动机**：解释约束背后的原因（“因为不能破坏已有用户登录态”比“不要修改认证逻辑”更有效）
4. **量化优先**：尽量使用数字、条件和验收标准（“降低20%”而非“降低一些”）
5. **区分确定性**：区分事实、推测和待确认信息，不虚构文件、接口、依赖或版本
6. **自包含性**：提示词应可以直接粘贴到新对话中使用，不需要执行者额外询问
7. **单一目标**：避免把多个互不相关的目标混在一个任务中
8. **功能原子性**：每个用户可感知的功能独立成条。不得因为 UI 上相邻就把多个功能写成一个入口（`设置 0–5 星、设置/清除颜色标记` 这类写法禁止）。确实需要合并时，必须显式写成一条设计决策并说明原因，由用户单独确认
9. **否定式条件**：对“不应存在的东西”，写“不存在 X，包括形式 A / B / C 与位置 L1 / L2”，与肯定式条件并列使用。只否定一种具体形式，会留下“换个形式加回来”的口子
10. **口头复用的翻译**：用户说“复用 X”“和 X 一样”时，必须译成防分叉条款——复用同一实现（点名组件与逻辑）、禁止平行副本、写明允许的最小参数化适配范围、写明原调用方行为与外观零变化的回归条件

## 引用项目文档的格式

```text
<project_context>
来源：README.md
内容：项目文档明确说明该项目用于……
注意：请在仓库中验证这些信息，文档可能已经过时。
</project_context>
```

不要把长篇文档原文直接放入提示词。只引用与任务相关的部分。
