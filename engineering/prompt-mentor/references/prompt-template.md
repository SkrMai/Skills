## 默认模板

用户放行前，按以下结构生成共识包。可以根据任务类型删除无关段落，但**不要删除 `<goal>`、`<acceptance_criteria>`、`<constraints>`**。

```markdown
<goal>
[用一句话说明最终目标，必须是可验证的完成标准]
</goal>

<optimized_requirement>
[阶段 1 锁定的优化后需求描述。若因探测微调，在微调处显式标注]
</optimized_requirement>

<requirement_list>
1. [原子化功能项]
2. [原子化功能项]
</requirement_list>

<verified_facts>
来源：[Subagent 探查 / AI 直读 <范围> / 用户确认]（已核实）
- [已核实的事实 1]
- [已核实的事实 2]
</verified_facts>

<unverified_assumptions>
- [未核实项]，由执行阶段核实
</unverified_assumptions>

<scope>
保留项（不得改动）：
- [功能项]

移除项：
- [功能项]（理由：[为什么移除]）

新增项：
- [功能项]

本次不处理：
- [功能项]（理由：[用户裁决为保留不动 / 以后再说]）
</scope>

<acceptance_criteria>
完成必须满足（Done when）：
- [ ] [可验证标准 1]
- [ ] [边界情况标准]

不应存在（逐项枚举位置与形式）：
- [ ] [对象] 中不存在 [不应存在的功能]，包括：[形式 1]、[形式 2]、[位置 1]、[位置 2]

保持不动：
- [ ] [保留项清单] 中的功能行为与外观零变化
</acceptance_criteria>

<constraints>
- 不得顺手重构保留项
- 实现位置由执行 agent 阅读代码后决定，并在方案中说明
- 不得新建平行组件（如涉及复用）
- [兼容性要求 / 不能改变的现有行为 / 性能或安全要求 / 依赖和技术限制]
</constraints>

<non_goals>
- [明确不处理什么]
</non_goals>

<uncertainties>
- [待执行阶段核实的项]
</uncertainties>
```

**不要写进共识包的东西：** 具体文件路径、组件名、函数名、`<task>` 段落、"涉及文件"列表、实现步骤、`<workflow>`、`<response_contract>`。执行流程与汇报格式由 `./references/stage4-execute.md` 统一规定，不需要在每份共识包里重述。

## 能力描述与实现位置留白

共识包描述**能力**，不描述**位置**。这是从"提示词"转向"共识包"之后最需要改掉的习惯：原来写 `<task>` 的地方，现在写能力描述；位置留给执行阶段。

| 要表达的意思 | ❌ 写成位置 | ✅ 写成能力 |
|------------|-----------|-----------|
| 拆开两个入口 | "修改 `<某个组件>` 的渲染逻辑" | "多选菜单中，星级与颜色标记是两个互不嵌套、互不触发的独立入口" |
| 复用已有能力 | "复用单选菜单里的 `<某个组件>`" | "星级必须复用单选菜单已有的星级能力与逻辑，同一份实现，不得新建平行实现" |
| 限定改动范围 | "只改 `<某个文件>`，其他文件不要动" | "保留项清单中的 5 项功能行为与外观零变化" |
| 说明落点由谁定 | "实现位置你看着办" | "实现位置由执行阶段阅读代码后决定，并在方案中说明选择理由" |

留白不等于含糊：**能力要写到能被验收的精度，位置一个字都不写。**

## 条件段落

### `<verified_facts>`（已核实）

只放**有证据**的事实。来源限定四种写法：

```text
来源：Subagent 探查（已核实）
来源：AI 直读 <范围>（已核实）
来源：用户确认
（文档来源不算已核实，见 <unverified_assumptions>）
```

每条事实写到"能被执行阶段直接当前提用"的粒度：

- ✅ `颜色标记作用于文件（非文件夹），仅在多选菜单暴露`
- ❌ `颜色标记的实现比较复杂`（不是事实，是评价）

### `<unverified_assumptions>`（未核实）

放三类内容：

1. 从文档读到但未核实的功能描述（附文档来源与可信度）
2. 探测盲区中与本次需求相关的部分
3. 用户无法确认、需要执行阶段在代码里查证的项

每条必须带"由执行阶段核实"的标注。**没有未核实项时写 `- 无`，不要省略这一段。**

两段必须分开写。混写的后果是执行阶段分不清哪些前提站得住，偏差会被固化。

## 修正类任务模板

用于**已经实现并交付、但有具体问题需要定点修正**的功能。不要用默认模板改写需求描述，直接用本结构。

核心是三段结构：**修正项 / 保持不动 / 否定式完成条件**。缺少任何一段，执行阶段都容易借小修做大改。

```markdown
<goal>
修正 [功能名] 的 [具体问题]，其余已实现部分保持零改动。
</goal>

<optimized_requirement>
[阶段 1 锁定的逐条结构化需求描述原文]
前置依赖：[无 / 共识包 1/N 的产出]
本次是定点修正，不是重构，也不是重新设计。
</optimized_requirement>

<requirement_list>
1. [修正项 1 的用户可感知结果]
2. [修正项 2 的用户可感知结果]
</requirement_list>

<verified_facts>
来源：[Subagent 探查 / AI 直读]（已核实）
- [该功能当前的实际行为]
</verified_facts>

<unverified_assumptions>
- [未核实项]，由执行阶段核实
</unverified_assumptions>

<scope>
保留项（不得改动）：
- [保持不动的部分 1]
- [保持不动的部分 2]

修正项：
1. [修正项 1]：当前 [现状]，期望 [期望结果]
2. [修正项 2]：当前 [现状]，期望 [期望结果]

本次不处理：
- [发现但不在本次范围内的问题]（理由：用户裁决只上报不修改）
</scope>

<acceptance_criteria>
修正项完成（Done when）：
- [ ] [修正项 1 的可验证结果]
- [ ] [修正项 2 的可验证结果]

不应存在（逐项枚举位置与形式）：
- [ ] [对象] 中不存在 [不应存在的功能]，包括：[形式 1]、[形式 2]、[位置 1]、[位置 2]

保持不动：
- [ ] 保留项清单中的功能行为与外观零变化
</acceptance_criteria>

<constraints>
- 不扩大修改范围（原因：修改范围越大，回归风险越高）
- 只验证以下三项，不扩大验证范围：修正项、否定式条件、保留项零变化
- 禁止修复保留项清单之外的任何问题；发现其他问题只上报，不修改
- 不得顺手重构、重命名、格式化保留项
- [其他约束]
</constraints>

<non_goals>
- [明确不处理什么]
</non_goals>

<uncertainties>
- [待执行阶段核实的项]
</uncertainties>
```

**使用要点：**

- 保留项清单必须显式写出功能名，不要用"其他功能"这种笼统表述
- 否定式条件必须枚举位置与形式（菜单项 / 子菜单 / 面板区块 / 设置项），只否定一种形式会留下"换个形式加回来"的口子
- 不要在修正类共识包里加入"顺便优化""如发现问题一并修复"这类开口条款
- 修正项的"当前行为"必须有证据支撑，来自探测或自己读代码，不得凭用户口述的现状直接当事实

## 框架选用决策树

```text
用户需求 →
├── 有明确的"做完标志"（测试通过 / 错误消失 / 指标达标）？
│   → 用 Goal Contract（见下方）
├── 需要定义角色和输出格式，且任务较复杂？
│   → 用完整模板 + Goal Contract 的验收标准
├── 只是解释 / 咨询 / 对比？
│   → 用简化模板（角色 + 任务 + 上下文 + 输出格式）
└── 不确定？
    → 默认用完整模板（可验证性优先）
```

## 各框架详解

### Goal Contract（核心框架）

Goal Contract 是 Goal Engineering 的核心框架。核心洞察与"可验证停止条件"的写作要求（否定式条件的枚举方式）见 `./references/stage3-consensus.md` §5.1，本节只给结构模板。

**结构：**

```markdown
【目标】
（一句话描述最终状态，必须可验证）

【当前状态】
（描述现状，包含已知的失败现象或差距）

【完成条件】（Done when）
- [ ] 条件1
- [ ] 条件2

【约束】
（绝对不能做的事 + 原因）

【方法建议】
（可选，给执行者提供思路但不强制）
```

**示例：**

用户原始需求："登录接口有时候报错，帮我修一下。"

```text
【目标】
修复登录接口的空指针异常，确保所有合法请求返回 200，非法请求返回明确的错误码。

【当前状态】
登录接口在部分请求下返回 500，日志显示 NullPointerException。

【完成条件】（Done when）
- [ ] 所有合法登录请求返回 200 + 用户信息
- [ ] 空参数请求返回 400 + 错误提示
- [ ] 新增 3 个以上边界情况的单元测试且全部通过
- [ ] 已有测试无回归

【约束】
- 不修改数据库表结构（原因：生产环境迁移成本高）
- 不改变现有 API 响应格式（原因：前端已依赖当前格式）
- 保持登录 token 生成逻辑不变
```

注意：示例里的"当前状态"在共识包里要落到 `<verified_facts>` 或 `<unverified_assumptions>`，并说清是哪一种。

### 验证者指令（Maker/Checker 分离）

阶段 4 的验收以独立视角进行，与实现思路分离。Goal Engineering 的 maker/checker 分离模式正是为了解决"看起来做完了"与"实际做完了"之间的差距。

```text
完成实现后，切换为验证者视角，独立检查：
1. 逐条对照 acceptance_criteria，用"是/否"标记每条是否满足
2. 逐条对照否定式条件（不存在 X，包括哪些形式与位置）
3. 运行所有相关测试，报告通过/失败数量和具体失败原因
4. 检查是否引入了非目标范围内的改动
5. 如果任何条件未满足，说明原因并继续修复，不要仅报告问题
```

这段是**阶段 4 的执行纪律**，不写进共识包。

### STCO 框架（适合新功能）

| 要素 | 含义 |
|------|------|
| Situation | 背景和角色 |
| Task | 具体任务（可衡量的输出） |
| Constraints | 边界和格式要求 |
| Output | 期望的结构和质量标准 |

STCO 的优势在于四要素互不重叠，适合需要明确定义角色和输出格式的场景。

### 轻量场景（代码解释 / 咨询）

适合不需要执行-验证循环的场景，使用简化模板：

```text
【角色】
你是一位[具体角色]，擅长[具体能力]。

【任务】
[明确描述需要完成的任务]

【上下文】
[只放与本任务相关的背景信息]

【输出格式】
[期望的输出结构]
```

## 写作规范细则

1. **明确具体**：用直接动作动词开头（"分析""生成""重构"）
2. **正向指导**：告诉执行阶段"要做什么"，而非"不要做什么"。正向指令的合规率更高
3. **提供动机**：解释约束背后的原因（"因为不能破坏已有用户登录态"比"不要修改认证逻辑"更有效）
4. **量化优先**：尽量使用数字、条件和验收标准（"降低 20%"而非"降低一些"）
5. **区分确定性**：区分事实、推测和待确认信息，不虚构文件、接口、依赖或版本
6. **可直接开工**：共识包应能让阶段 4 的执行角色直接动手，不需要反过来问用户。需要它自己查证的项，写进 `<uncertainties>`
7. **单一目标**：避免把多个互不相关的目标混在一份共识包里
8. **功能原子性**：每个用户可感知的功能独立成条。不得因为 UI 上相邻就把多个功能写成一个入口（`设置 0–5 星、设置/清除颜色标记` 这类写法禁止）。确实需要合并时，必须显式写成一条设计决策并说明原因，由用户单独确认
9. **否定式条件**：对"不应存在的东西"，写"不存在 X，包括形式 A / B / C 与位置 L1 / L2"，与肯定式条件并列使用。只否定一种具体形式，会留下"换个形式加回来"的口子
10. **口头复用的翻译**：用户说"复用 X""和 X 一样"时，必须译成防分叉条款——复用同一实现（点名要复用的是哪部分能力或逻辑）、禁止平行副本、写明允许的最小参数化适配范围、写明原调用方行为与外观零变化的回归条件

## 引用项目文档的格式

文档内容进 `<unverified_assumptions>`，写法：

```text
来源：[README.md / AGENTS.md 等]
文档原文声称：[文档里怎么说的]
可信度：[低 / 中]——[为什么不能直接采信]
处置：由执行阶段在代码中确认后再实现
```

用户确认过、或探测核实过的文档内容，才升级进 `<verified_facts>`，并把来源改写为"用户确认"或实际的核实来源。

不要把长篇文档原文直接放入共识包。只引用与任务相关的部分。
