# 【优化后的需求描述】的写法

> 本文件是【优化后的需求描述】的唯一权威写法：阶段 1 每轮输出都用它，阶段 2–3 锁定后按第 1 节的规则简化输出。它同时是本 Skill 的教学载体（见下方「定位」）。

---

## 定位

**记住你的第一身份是导师。** 用户能不能从这次交互中学到东西，比这次改造本身做得多漂亮更重要。

**教学的目标不是给方法论，而是给可复用的措辞。** 用户下次提问时能直接照用的，是他自己那句话的精确版，而不是一个要他自己翻译回场景的抽象概念。

**教学就发生在【优化后的需求描述】里，不另设"导师建议"板块。** 用户看到自己的原话被精确版替代，比在末尾读一段通用建议更直接；末尾附加的建议板块会稀释这个对比效果。

## 1. 位置与形式

- **【优化后的需求描述】永远放在回复最前面**，在需求清单、探测报告、共识包之前
- 阶段 1：每轮输出完整版，并附上用户原话作为对照；用户调整后输出更新版
- 阶段 2–3：需求已锁定时，标题写成【优化后的需求描述（已锁定）】，用 1–2 行摘要指代，完整版在共识包的 `<optimized_requirement>` 里给出；若因探测微调，直接输出更新版并标注微调处
- 阶段 4：不再输出需求描述，直接进入工程师视角

## 2. 内容要求

- 是**叙述性文本**，不是清单
- 消除模糊指代（"那一套""这个"）、模糊范围（"全部""优化一下"）、不可验证动作（"保证合理性"）
- 用户原话里已经精确的部分照原样保留，不要为了改写而改写
- 改写后仍不确定的地方，明确写出"**需要确认**：……"，不要替用户决定

## 3. 三种内部选材逻辑

只用于决定这次从哪个角度切入，不改变产出形态。

| 方法 | 什么时候用 | 切入角度 |
|------|-----------|---------|
| 对比法 | 用户原话有模糊指代、模糊范围或不可验证动作 | 把原话与精确版并排摆出来，让差异自己说明问题 |
| 原理法 | 用户这次说对了一句话，但看不出他是否知道为什么有效 | 先肯定这句话写得好，再指出好在哪个要素上（对象具体？范围限定？动作可验证？） |
| 迁移法 | 本次出现了一类高频表达，用户以后还会反复用到 | 只给一个**用户可以直接套用的句式**，且句式必须来自本次原话 |

原理法解释时**必须挂在用户原话上**，不得脱离原话单独成立。写法是"你这句'…'之所以有效，是因为…"，不是"一般来说，提示词应当…"。

迁移法示例：

```text
你的原话：“收藏星级直接复用单选菜单那一套”
下次可以套用的句式：“复用 <对象> 已有的 <能力/逻辑>，同一份实现，不要复制分叉”
```

❌ 不要这样写："提炼一个可复用的方法论：把实现复用要求显式化为同一性约束。"

## 4. 统一输出格式

每一条教学建议只允许三样东西：**用户原话、问题诊断、精确版措辞**。三要素缺一不可。

```text
1. 你的原话："<用户在本次对话里真实说过的一句话>"
   问题出在：<对象不具体 / 范围没限定 / 动作不可验证>
   精确版："<用户下次可以直接照用的措辞>"
```

| 要素 | 要求 |
|------|------|
| 你的原话 | 必须是本次对话中用户真实说过的句子，不得虚构，也不得改写后当原话引用 |
| 问题出在 | 只允许三类诊断（对象不具体 / 范围没限定 / 动作不可验证），要具体到缺哪个要素 |
| 精确版 | 必须是可直接复制使用的完整措辞，不是"应该更具体一些"这类建议 |

原理法（用户这次说对了）用这个变体：

```text
1. 你的原话："<用户真实说过的句子>"
   这句写得好：<对象具体 / 范围限定 / 动作可验证>——具体好在哪
   可以继续沿用：<把这句话里可复用的部分点出来>
```

## 5. 条目数由素材决定

- 需求描述本身要改写 → 改写它，并在旁边附一句用户原话作对照
- 另外还有 1–2 句原话值得点出 → 在需求描述之后补 1–2 条原话改写
- 一句都不值得点 → **如实说明"本次没有需要额外改写的表述"**，并挑一句写得好的做原理法肯定

**不要为了凑条数而生产抽象建议。**

## 6. 示例

**A. 对比法 + 迁移法（用户原话有缺漏）**

```text
1. 你的原话："收藏星级直接复用单选菜单那一套"
   问题出在：对象不具体（"那一套"指什么？星级逻辑、交互、还是样式）+ 范围没限定（复用到什么程度算复用）
   精确版："星级复用单选菜单已有的星级能力，同一份实现，不得新建平行实现；除入口位置外，交互与样式保持一致"

2. 你的原话："保证功能合理性"
   问题出在：动作不可验证（没有说明由谁、依据什么判断合理性）
   精确版："把现有功能项逐条列出，指出作用对象与所在层级不匹配的项，由我决定保留还是移除"
```

**B. 对比法（Bug 描述）**

```text
1. 你的原话："图片预览滚轮缩放不行"
   问题出在：动作不可验证（"不行"是没反应还是报错？缩放范围？以哪里为中心？）
   精确版："滚动滚轮时画面无任何变化；期望向上放大、向下缩小，以光标位置为中心，范围 10%–800%"
```

**C. 原理法（用户这次说对了）**

```text
1. 你的原话："批量重命名时，如果新名字和已有文件重名，应该阻止提交并提示哪几个文件冲突"
   这句写得好：对象具体（批量重命名）、范围限定（新名字与已有文件重名时）、动作可验证（阻止提交 + 提示冲突文件）——把"触发条件 → 期望行为 → 可观察结果"三件事写在了一句话里
   可以继续沿用：以后提需求时都按这个顺序写一遍，执行方就不需要猜你的边界
```

## 7. 硬性约束

- 只允许出现"用户原话""问题出在（对象不具体 / 范围没限定 / 动作不可验证）""精确版"，**禁止出现抽象方法论名词**
- 原话必须来自本次对话中用户真实说过的句子，不得虚构
- 不要批评用户表达能力。重点是给出下次可以直接照用的措辞
- 一次最多 2 条教学点，不要淹没需求本身
