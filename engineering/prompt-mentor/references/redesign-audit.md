## 一、为什么需要这一节

重设计任务最常见的失败不是"设计得不好看"，而是**把现有实现里的不合理原样带进了新设计**。

失效链条：

```text
用户说"重新设计 X"
→ 没盘点 X 现在有什么
→ 项目里预存的不合理（同类对象之间的不对称、作用域错配）没被发现
→ 错误文档反而成了设计许可
→ 不合理被原样延续，甚至被"顺手优化"成更严重的合并
→ 执行阶段照做，用户验收时才发现
```

根因：把"重新设计"当成了纯写作任务。重新设计的第一步永远是**探测与审计**，不是写新方案。

**红线：未取得现状清单（或未显式声明盲区），不得生成共识包。**

## 二、触发条件

出现任一条件即按本流程处理：

- 用户表述含：重新设计、重做、改版、改造、重构交互、调整一下现有的、优化现有、重新组织、梳理
- 用户点名要实现的新功能，**看起来已经存在于该对象中**
- 用户描述的是"让 X 更合理"，但没有说明 X 现在是什么样
- 用户说不出被改对象的现有功能项

**与其他任务类型的区分**：

| 用户表述 | 任务类型 | 是否需要本流程 |
|---------|---------|-------------|
| "重新设计多选右键菜单" | 重设计已有功能 | ✅ 必须 |
| "给多选菜单增加批量重命名" | 新功能 | ❌ 不需（但要查重：该功能是否已存在） |
| "多选菜单里的颜色标记有问题" | Bug 修复 | ❌ 不需（但要查作用域是否本来就该在这） |

## 三、探测与审计流程

### 3.1 第一步：层一判断是否需要探测

判据见 `./references/stage2-probe-audit.md` 第 2 节。重设计类任务几乎必然不满足第 2 个必要条件（涉及对已有对象的重新设计），所以**默认需要探测**。

### 3.2 第二步：层二判断探测由谁执行

判据见 `./references/stage2-probe-audit.md` 第 3 节。重设计任务通常同时命中"并发"（主对象 + 对照对象 + 实现路径）与"上下文"（产出量大），**倾向派 Subagent**；总数仍控制在 2–4 个。

### 3.3 第三步：探测要拿到什么

现状清单必须回答四个问题：

- 被重新设计的对象叫什么？在界面的哪个位置？
- 它有几个变体？（单选 / 多选；文件 / 文件夹；列表 / 详情）
- 现有功能项清单是什么？（名称 / 作用对象 / 出现位置 / 证据）
- 有没有同类对象可以对照？（另一个菜单、另一种条目类型、另一个页面）

**取得清单的三种方式，按优先级：**

1. **探测核实**（首选）——自己读或派 Subagent，产出可写进 `<verified_facts>`
2. **用户直接给出清单**——写进 `<verified_facts>`，来源标注"用户确认"
3. **探测与用户都拿不到**——按第六节注入执行侧兜底段落，并在 `<uncertainties>` 中声明

⚠️ 不要让用户去翻代码给你抄清单。用户给的是**他的认知**，不是代码事实；能自己核实的就自己核实，核实不了就标注清楚。例外：**用户在界面上能直接观察到的事实**（入口位置、当前行为、哪种选择状态可用），且只需要问 1–2 条时，直接问用户比派 Subagent 更省——这不属于"翻代码抄清单"。

### 3.4 第四步：审计（三查）

见第四节。三查的产出是**待裁决项**，不是导师的结论。

### 3.5 第五步：向用户裁决

把每条不合理摆到用户面前，给出：

- 现状描述
- 为什么不合理（对称性 / 归属 / 冲突）
- 三种处置：保留（有理由）/ 移除 / 待定
- 建议倾向及理由

**必须给出可选项让用户裁决**，不要只描述问题。

**不得默认保留。不得自行决定。不得仅口头提一句"顺便说下这里可能有点问题"就继续往下做。**

### 3.6 第六步：写进共识包

| 产物 | 去向 |
|------|------|
| 探测到的现状盘点表 | `<verified_facts>`（逐条标来源） |
| 用户裁决结果 | `<scope>` 的保留项 / 移除项 / 本次不处理 |
| 探测盲区中与需求相关的部分 | `<unverified_assumptions>` + `<uncertainties>` |
| 用户裁决为"以后再说"的项 | `<non_goals>` |
| 探测与用户都拿不到的部分 | 按第六节注入执行侧兜底段落 |

## 四、三查清单

对现状清单里的**每一项**问三个问题。

### 4.1 对称性查

> 同类对象之间，有哪些功能项一边有一边没有？这个不对称是有意的吗？

典型场景：

- 单选菜单有 A，多选菜单没有 A
- 多选菜单有 B，单选菜单没有 B
- 文件条目有 C，文件夹条目没有 C
- 列表页有 D，详情页没有 D

发现不对称时，必须问用户：**这是产品有意的设计，还是历史遗留？** 有意的保留并写进 `<constraints>` 说明理由；历史遗留的按归属查继续判断。

**基线判断**：当一边是独立项、另一边是合并项时，通常**独立的那一边是基线**，合并的那一边是偏离。把结论作为待裁决项交给用户，不要直接下判断。

### 4.2 归属查

> 这一项的作用对象与它所在的层级匹配吗？

判据：功能的作用对象（单个文件 / 文件列表 / 文件夹 / 整个工作区）是否与承载它的入口层级一致。

作用域错配的典型形态：

- 文件夹维度的功能出现在文件级菜单里
- 单个对象的功能出现在批量菜单里（或反之）
- 全局设置出现在局部菜单里

发现错配时：指出 → 用户裁决 → 决定移除、迁移到正确层级，或保留并说明理由。

### 4.3 冲突查

> 用户点名的新功能与现有功能是否重复或语义重叠？

典型场景：

- 用户要的"批量 X"其实已存在，只是名字不同
- 两个现有项语义重叠（收藏 / 标记 / 星标）
- 新功能会取代某个现有项的功能

发现冲突时：指出 → 用户裁决 → 在 `<scope>` 中写明是替换、并存还是合并。**合并必须作为待确认项单列进【需要确认】，由用户单独确认。**

## 五、裁决表模板

放在回复的【现状审计】一节，作为交给用户裁决的输入：

```text
【现状盘点】对象：<被重新设计的对象>（变体：<单选 / 多选 / 文件 / 文件夹>）
来源：<Subagent 探查 / AI 直读 / 用户确认 / 未取得（见 uncertainties）>

| # | 现有项 | 现状作用对象 | 对称性 | 归属 | 处置 | 理由 |
|---|--------|-------------|--------|------|------|------|
| 1 | 批量重命名 | 多个文件 | 仅多选有 | 匹配 | 保留 | 作用域正确 |
| 2 | 设置颜色标记 | 多个文件 | 仅多选有 | ⚠️ 错配 | 移除 | 颜色标注属于文件夹维度 |

待裁决项：
T1. [不对称项]：现状是……；可选处置：一并处理 / 保留不动 / 待定
T2. [错配项]：现状是……；可选处置：迁移层级 / 保留并说明理由
```

处置列只允许四种值：**保留 / 移除 / 改 / 待探测核实**。合并写成"改"，并在【需要确认】中单列。

裁决结果确认后写进 `<scope>`：

- 保留 → `<scope>` 的保留项
- 移除 → `<scope>` 的移除项（**必须附理由**）
- 保留不动 / 以后再说 → `<non_goals>`
- 待探测核实 → `<unverified_assumptions>` + `<uncertainties>`

## 六、执行侧兜底段落模板

**用途**：当探测无法覆盖、用户也提供不了完整清单时（Subagent 也查不到、对象过于分散、项目结构不可读），把盘点责任下移到阶段 4，作为执行角色的第一步硬约束。

**放法**：不新增共识包段落。把下面的要求合并成 `<uncertainties>` 中的条目，并在 `<constraints>` 中加一条硬约束"实施任何修改之前，先完成现状盘点并汇报，不要跳过这一步直接改代码"。

### 6.1 现状盘点要求

```text
实施任何修改之前，先完成盘点并汇报，不要跳过这一步直接改代码。

1. 在代码中列出现有 <对象> 的全部功能项（菜单项、子菜单、面板区块、快捷键），逐项给出：
   - 名称
   - 作用的对象类型（单个文件 / 文件列表 / 文件夹 / 其他）
   - 出现位置（哪个菜单、哪个层级）
2. 对照同类对象：<同类对象> 有哪些项是本对象没有的？本对象有哪些项是同类对象没有的？
3. 逐项判断作用域是否与所在层级匹配。
4. 盘点结果以表格形式汇报，作为后续实施的第一步产出。
```

### 6.2 不合理项的上报要求

```text
盘点中发现的不合理项（作用域错配、同类对象不对称、与本次需求重叠）必须：
- 逐条列出，说明为什么不合理，给出处理建议
- 在用户确认前，**不得自行决定移除或保留**
- 不得为了让设计"更整齐"而顺手合并功能项

如果盘点结果与本次需求描述冲突，先停下来报告冲突，不要按需求描述硬做。
```

### 6.3 与设计内容的关系

盘点是设计的**输入**，不是设计的替代。盘点完成后：

- 用户已裁决的项 → 按裁决结果执行
- 用户未裁决的项 → 保留现状，并在汇报中列为待确认项
- 需求中点名要移除的项 → 必须在盘点清单中逐项列出并说明移除理由

## 七、验收标准写法

重设计任务的 `<acceptance_criteria>` 必须包含以下三类。

**1. 现有能力清单完整性（防止静默消失）**

```text
- [ ] 重新设计后，<对象> 的现有能力无一项静默消失：
      <逐项列出保留的能力>
- [ ] 每一项被移除的能力都在 scope 的移除项中列出，并附移除理由
```

**2. 否定式条件（防止换个形式加回来）**

```text
- [ ] <对象> 中不存在 <不应存在的功能>，
      包括：菜单项、子菜单、面板区块、设置项、快捷键（逐一枚举位置与形式）
```

**3. 对称性条件（如果本次要修正不对称）**

```text
- [ ] <对象 A> 与 <对象 B> 在 <功能维度> 上一致：<具体一致性要求>
```

**反例**（不要这样写）：

```text
❌ 菜单设计合理          —— 无法用是/否判断
❌ 保持现有功能不变      —— 无法验证，且与"重新设计"矛盾
❌ 移除颜色标记          —— 只否定一种形式，颜色仍可藏在星级面板里
```

## 八、反模式

- ❌ 重设计前不探测现状，直接写新方案
- ❌ 探测了但不做合理性判断，原样照搬
- ❌ 发现不合理却只在对话里提一句，未让用户裁决就继续
- ❌ 把"现状是什么样的"整个推给执行阶段，导师侧一句不问
- ❌ 让探查 Subagent 顺带给改进建议或裁决
- ❌ 审计后自行决定移除或合并（用户没裁决）
- ❌ 验收标准只写"设计合理""功能正常"，不写"现有能力无一项静默消失"
- ❌ 拿到错误文档就当现状事实（文档只能作为待验证线索，见 SKILL.md 第 2.5 节）
- ❌ 把"重新设计"做成"新增一版并存"（旧对象没删干净，两套菜单并存）
