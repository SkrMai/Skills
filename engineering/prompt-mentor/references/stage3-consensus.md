# 阶段 3：共识包生成 + 用户放行

> **本文件是阶段 3 的唯一权威规则**，进入阶段 3 前完整读一遍。
> 共识包逐段规范见 `./references/consensus-package.md`；可复制填空的模板骨架见 `./references/prompt-template.md`；多份共识包的组织见 `./references/prompt-count-decision.md`。
> 本阶段只生成共识包并请求放行，不改项目。

---

## 1. 目的与输入

**目的**：把前两阶段的成果固化成一份**自包含的共识记录**，作为执行阶段的唯一依据。

## 2. 共识包结构

整合四类输入生成共识包：阶段 1 锁定的需求描述、阶段 1 锁定的需求清单、阶段 2 的探测结果（已核实 / 未核实）、阶段 2 的审计裁决结果。

**轻量通道下可以省略空段落**（判据见 `SKILL.md` 第 4.2 节）：`<verified_facts>`、`<unverified_assumptions>`、`<scope>`、`<non_goals>` 四段在**确无内容**时可整段省略；`<goal>`、`<optimized_requirement>`、`<requirement_list>`、`<acceptance_criteria>`、`<constraints>`、`<uncertainties>` 一律不得省略。省略只针对空段落，不降低任何一条判据。

```markdown
<goal>一句话可验证目标</goal>

<optimized_requirement>
阶段 1 锁定的优化后需求描述（若因阶段 2 微调，标注微调处）
</optimized_requirement>

<requirement_list>
阶段 1 锁定的原子化需求清单
</requirement_list>

<verified_facts>
已核实事实（来自探测），每条标注来源
</verified_facts>

<unverified_assumptions>
未核实项，标注"由执行阶段核实"
</unverified_assumptions>

<scope>
保留项：逐条列出
移除项：逐条列出，附理由
新增项：逐条列出
本次不处理：逐条列出
</scope>

<acceptance_criteria>
完成必须满足（Done when）：
- [ ] 可验证标准
- [ ] 否定式条件：不存在 X，包括 A/B/C 形式与 L1/L2 位置
- [ ] 现有能力无一项静默消失

保持不动：
- [ ] 保留项清单中的功能行为与外观零变化
</acceptance_criteria>

<constraints>
- 不得顺手重构保留项
- 实现位置由执行 agent 阅读代码后决定，并在方案中说明
- 不得新建平行组件（如涉及复用）
- [其他项目约定]
</constraints>

<non_goals>明确不处理什么</non_goals>

<uncertainties>待执行 agent 核实的项</uncertainties>
```

完整结构与逐段生成规则见 `./references/consensus-package.md`；可直接复制填空的模板骨架见 `./references/prompt-template.md`。

## 3. 生成规则

- **无 `<task>` 段落。** 共识包不写"改哪个文件、用什么组件、怎么实现"
- **禁止出现具体文件路径、组件名、函数名**，除非用户明确点名要求复用——那种情况也要转成防分叉条款（见 `./references/stage1-clarify.md` 第 4 节），而不是写成"改某文件"。允许**模块 / 能力层级**的边界措辞（见 `./references/consensus-package.md` 第三节）
- **已核实事实与未核实假设分开写**，这是核心机制：防止把文档或猜测当成事实带进执行
- `<scope>` 只写功能项层级的保留 / 移除 / 新增，不写实现文件
- 修正类任务用三段结构（修正项 / 保持不动 / 否定式条件），见 §5.4
- 生成后逐项核对 `./references/quality-checklist.md`

## 4. 放行门槛

把完整共识包摆给用户，明确请求放行：

```text
以上共识包是否正确？请选择：
1）回复"确认"——锁定共识包，先不执行（之后随时说"开始执行"再进入执行）；
2）回复"开始执行"——锁定并立即切换为资深工程师角色开始改造。
如需调整，直接指出。
```

**放行必须弹出来让用户点**（环境提供交互式提问工具时，规则见 `SKILL.md` 第 5 节）：一次调用给三个选项——`确认`（锁定共识包，先不改代码，之后随时说"开始执行"）、`开始执行`（锁定并立即切换为资深软件工程师角色）、`需要调整`（用户指出要改哪几条）。推荐项按当前交付模式：模式 A（默认）推荐 `开始执行`，模式 B 推荐 `确认`；推荐项放第一个并加 `(Recommended)`。选项标签与上面正文里的措辞逐字一致，正文的放行请求照常输出。

用户拒绝某条后，修订版必须**真正移除**该条，不得改写成其他形式保留。

**放行有四个方向**：

- **用户确认 → 锁定共识包**：模式 B（只交付共识包）到此结束；模式 A 等用户说"开始执行"再进入阶段 4
- **用户说"开始执行" → 锁定并进入阶段 4**
- **用户拒绝某条 → 修订后重新出共识包**（不得就地模糊处理）
- **用户提出需求层面的调整 → 回阶段 1**，不在阶段 3 就地改写共识包

**放行前不得开始任何修改。** 用户逐项修改后表示没有其他问题，视为放行（锁定）。

## 5. 共识包设计原则

### 5.1 核心原则：可验证的停止条件（肯定式 + 否定式）

无论共识包用什么结构，都必须包含明确的"完成定义"。大多数 agent 会话在"模型听起来做完了"时就结束了，但测试可能失败、迁移可能未完成。可验证的完成条件解决两个问题：agent 太快放弃，或 agent 无限循环做无方向的修改。

核心洞察：**好的共识包不是告诉执行者"做什么"，而是定义执行者"做到什么程度才算完"。**

- 什么状态下，执行者可以确认任务已完成？
- 每一条完成条件，是否可以用"是/否"来判断？
- 如果一条条件无法用是/否判断，说明它还不够具体

对"不应存在的东西"，必须写否定式条件：不存在 X，**包括形式 A、B、C 与位置 L1、L2**。

- ❌ 只写肯定式：`星级是独立菜单项` —— 颜色入口仍可能以其他形式出现，例如嵌在星级面板里
- ✅ 否定式：`菜单中不存在任何颜色标注入口，包括菜单项、子菜单、面板区块、设置项`

否定式条件的写作要求：

- **枚举位置与形式**，而不只是否定一个具体实现。"不存在 X"必须展开成"不存在 X，包括 A / B / C 形式与 L1 / L2 位置"
- 与肯定式条件**并列使用**，不是替代
- 同样必须可以用"是/否"判断
- 常用于封堵：换个形式加回来、藏在面板里、作为子选项出现、以别名或同义入口重现

### 5.2 关于框架

GOAL、SPF、CO-STAR、STCO 等可以作为记忆工具，但不是必须遵守的行业标准。根据任务选择结构：

| 任务类型 | 建议重点 |
|---------|---------|
| Bug 修复 | 现象、复现、证据、预期、根因分析、回归验证 |
| 新功能 | 用户、场景、行为、边界、范围、验收标准 |
| 重构 | 保持不变的行为、重构目标、风险、验证方式 |
| 性能优化 | 基线、瓶颈证据、目标指标、测量方法 |
| UI 调整 | 页面、用户流程、交互状态、响应式和可访问性 |
| 代码解释 | 对象、解释深度、读者水平、输出结构 |
| 通用任务 | 目标、上下文、约束、验收、输出格式 |

框架决策树、STCO 与 Goal Contract 的展开见 `./references/prompt-template.md`。

### 5.3 写作规范

- 用明确的动作动词描述需求
- 将愿望转化为可观察的结果
- 区分"必须""应该"和"可选"
- 尽量使用数字、条件和验收标准
- 区分事实、推测和待确认信息
- **不虚构文件、接口、依赖、版本或现有行为**
- 只引用与任务相关的项目文档
- 对文档中的信息注明"由执行阶段在代码中确认"
- 避免没有实际作用的角色包装和空泛形容词
- 避免把多个互不相关的目标混进一份共识包

引用项目文档时：

```text
来源：README.md
内容：项目文档明确说明该项目用于……
可信度：中等，尚未核实
```

不要把长篇文档原文直接放进共识包。

### 5.4 修正类任务（对已交付功能的定点修正）

当用户要修正**已经实现并交付**的功能时（"多选菜单里收藏和颜色被合并了，这是错的""预览缩放还是不行"），任务不是重做，而是定点修正。这类任务必须用三段结构，否则执行角色极易借小修做大改。

**必须写出的三段：**

1. **修正项**：逐条列出要改什么，每条写出"当前行为 → 期望行为"
2. **保持不动**：显式列出已实现且无问题的部分，并写一句硬约束——**禁止修复本清单之外的任何问题，不得顺手重构、重命名、格式化**
3. **否定式完成条件**：对"不应存在的东西"写带枚举位置的否定条件（§5.1）

```text
<corrections>
1. 拆分收藏与颜色标记：当前「批量收藏/星级」同时承担星级与颜色两种功能，期望拆成两个独立入口
2. 移除颜色标记入口：见 acceptance_criteria 的否定式条件
</corrections>

<do_not_touch>
以下部分已实现且无问题，本次不得改动，也不得顺手重构：
- 批量重命名
- 批量丢回收站
- 批量打标签
- 复制路径
- 重新解析

禁止修复本清单之外的任何问题。发现其他问题只上报，不修改。
</do_not_touch>

<acceptance_criteria>
- [ ] 星级是独立菜单项，0–5 星可设置
- [ ] 不存在任何颜色标注入口，包括菜单项、子菜单、面板区块、设置项
- [ ] 上述"保持不动"清单中的功能行为与外观零变化
</acceptance_criteria>
```

**验证范围限定**：只验证修正项 + 保持不动清单 + 否定式条件三项，不扩大验证范围，不因"顺便发现"而追加修改。这条写进 `<constraints>`。

完整模板见 `./references/prompt-template.md`。

### 5.5 重设计类任务的额外要求

重设计已有对象时，现状盘点与审计在阶段 2 完成（见 `./references/stage2-probe-audit.md`），产出：

- 探测结果 → `<verified_facts>`
- 用户裁决结果 → `<scope>` 的保留项 / 移除项清单
- 未覆盖的部分 → `<unverified_assumptions>` + `<uncertainties>`，并按 `./references/redesign-audit.md` 第六节注入执行侧盘点兜底段落

`<acceptance_criteria>` 必须包含"现有能力无一项静默消失"。

## 6. 标准回答模板（阶段 3）

````text
【优化后的需求描述（已锁定）】
[1–2 行摘要]

【共识包】
```markdown
[完整共识包]
```

【质量自检】
- ✅ 包含可验证的完成条件
- ✅ 包含否定式条件，并枚举了形式与位置
- ✅ 已核实事实与未核实假设分开
- ✅ 无文件路径 / 组件名 / 函数名
- ✅ 已经过 ./references/quality-checklist.md 逐项核对

【放行确认】
以上共识包是否正确？回复"确认"或"开始执行"，我切换到资深工程师角色开始改造。
如需调整，直接指出。
````

**任务数为 N>1 时**，在【共识包】之前加【共识包总览】（拆分理由、每份的目标、依赖关系、建议执行顺序、命名 `共识包 1/N：<标题>`），并说明这些共识包逐份执行。模板见 `./references/prompt-count-decision.md`。
