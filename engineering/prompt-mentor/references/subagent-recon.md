## 一、为什么要探测

文档只说明"项目是什么"，不说明"当前功能长什么样、入口在哪、作用于哪类对象"。凭文档猜结构，写进指向性很强的需求描述，执行阶段就会照着一个错误前提往下做，偏差被固化。

探测解决三件事：

- 用户描述里的**现状假设**是否成立（"这个功能已经有了""它作用于文件"）
- 同类对象之间**是否对称**（对照对象能暴露单看一个对象看不出的偏离）
- 敏感操作**实际作用于哪类对象、暴露在哪一层级**

探测的产物是**事实**，不是判断。判断发生在审计（`./references/stage2-probe-audit.md` 第 6 节）。

## 二、层一：是否需要探测

三个必要条件的判据见 `./references/stage2-probe-audit.md` 第 2 节。本节只列判断示例。

判断示例：

| 需求 | 需要探测吗 | 理由 |
|------|-----------|------|
| "新增批量导出 CSV" | 可能不需要 | 前提是"该功能不存在"这条假设已被用户确认，且无同类对照 |
| "把多选菜单里的收藏和颜色拆开" | 需要 | 涉及重设计 + 有单选菜单作对照 + 现状假设未核实 |
| "修一下图片预览滚轮缩放" | 需要 | 现状假设（滚轮无反应 / 只能放大 / 位置错乱）未核实 |
| "给设置页加一个开关" | 通常不需要 | 纯新增，无对照对象 |

## 三、层二：探测由谁执行

四个维度（耗时 / 并发 / 上下文 / 任务复杂度）的判据与判定规则见 `./references/stage2-probe-audit.md` 第 3 节。本节只列典型结构。

典型的三 Subagent 结构（主对象 + 对照对象 + 实现路径）：

```text
需求：拆分多选右键菜单里被合并的「收藏/星级」与颜色标记

探测发起：预计 3 个 Subagent
├── Subagent A：探查多选菜单（主对象）
├── Subagent B：探查单选菜单（对照对象）
└── Subagent C：探查颜色标记的完整实现路径（作用于哪类对象、在哪暴露）
```

## 四、探测前告知用户

规则（一句话告知、**这是告知不是征询**、用户喊停就核对方向）见 `./references/stage2-probe-audit.md` 第 4 节。下面是填好的示例：

```text
我要探测「文件右键菜单」的现状，重点确认三件事：多选菜单现有功能项、单选菜单作为对照、
颜色标记的作用对象与层级。
预计 3 个 Subagent：
- Subagent A：探查多选菜单（文件）
- Subagent B：探查单选菜单（文件）作为对照
- Subagent C：探查颜色标记的完整实现路径
开始探测。
```

自己读（不派 Subagent）时同样告知一句："我自己读 N 个文件核实 X，不派 Subagent。"

## 五、输入模板

每次派发都发这一段完整契约，不要口头带过：

```markdown
<recon_task>
对象 / 位置线索 / 变体 / 对照对象 / 探查范围
</recon_task>

<recon_boundary>
只做事实收集，不做设计判断。禁止：提出改进建议、判断功能该不该在这里、
合并或归类功能项、给出实现方案。发现可疑项时只标记，不裁决。
不要向用户提问：需要用户拍板或你无法确认的问题，写进返回结果第 4 节的「探查范围与盲区」，由主 Agent 汇总后统一询问用户。
</recon_boundary>

<recon_output_required>
1. 功能项清单（名称 / 作用对象 / 出现位置 / 证据）
2. 对称性对照（与对照对象逐项比对）
3. 可疑项标记
4. 探查范围与盲区
</recon_output_required>
```

### 5.1 `<recon_task>` 的写法

| 字段 | 要写什么 | 反例 |
|------|---------|------|
| 对象 | 被探查的功能对象叫什么 | "看看菜单那块" |
| 位置线索 | 界面上/代码里的入口线索 | 省略位置线索，让 Subagent 全库乱翻 |
| 变体 | 已知有哪几个变体（单选/多选、文件/文件夹） | 只提一个变体，漏掉对照 |
| 对照对象 | 用来比对的同类对象 | 只说主对象，不做对照 |
| 探查范围 | 明确"只查什么、不查什么" | 不给边界，产出大量无关内容 |

写全的例子：

```markdown
<recon_task>
对象：文件多选右键菜单
位置线索：文件列表区域的多选状态下右键唤出的菜单
变体：单选右键菜单（作为对照）、文件夹右键菜单（本次不查）
对照对象：文件单选右键菜单
探查范围：菜单项清单与它们的出现位置、层级、作用对象；不查菜单的渲染样式与快捷键实现
</recon_task>
```

## 六、输出模板

要求 Subagent 严格按此结构返回：

```markdown
## 探查报告：<对象名>

### 1. 功能项清单

| # | 功能项 | 作用对象 | 出现位置 | 证据 |
|---|--------|---------|---------|------|
| 1 | | | | |

### 2. 对称性对照

| # | 功能项 | 本对象 | 对照对象 | 差异 |
|---|--------|--------|---------|------|
| 1 | | | | |

### 3. 可疑项标记

- [ ] 作用对象与层级可能不匹配
- [ ] 与对照对象不对称
- [ ] 与本次需求可能重叠
- [ ] 用户描述与代码现状不符

### 4. 探查范围与盲区

- 已覆盖：
- 未覆盖（盲区）：
```

### 6.1 字段要求

- **作用对象**：单个文件 / 文件列表 / 文件夹 / 整个工作区 / 其他
- **出现位置**：哪个菜单、哪一层级（顶层项 / 子菜单 / 面板区块 / 设置项）
- **证据**：文件路径 + 行号，或可直接复核的定位信息。没有证据的条目视为未核实
- **可疑项标记**：只打勾，不写结论、不写建议

## 七、边界约束

**Subagent 只做事实收集，不做设计判断。** 明确禁止：

- ❌ 提出改进建议（"建议把这两项合并"）
- ❌ 判断某个功能该不该在这里
- ❌ 合并或归类功能项
- ❌ 给出实现方案
- ❌ 决定保留还是移除
- ❌ 向用户提问（Subagent 与用户之间没有交互通道，工具会以 `DELEGATED_CALLER` 拒绝）；未决问题写进返回结果，由主 Agent 汇总后统一弹出

发现可疑项时**只标记，不裁决**。裁决权在用户（`./references/stage2-probe-audit.md` 第 7 节分流）。

原因：一旦 Subagent 开始给建议，返回的就不再是事实，而是另一份未经验证的设计意见；导师再基于它做审计，误差会被叠加两次。

---

## 八、导师接法

拿到探查报告后：

1. **核对证据**：没有证据的条目降级为未核实，不得直接进 `<verified_facts>`
2. **做审计**（需要时）：三查——对称性 / 归属 / 冲突（`./references/stage2-probe-audit.md` 第 6 节，细则见 `./references/redesign-audit.md`）
3. **分流**（`./references/stage2-probe-audit.md` 第 7 节）：
   - 与用户需求冲突 → 回阶段 1 核对
   - 需求之外的不合理 → 交用户裁决
   - 信息已足够 → 进入阶段 3
4. **写进共识包**：
   - 已核实事实 → `<verified_facts>`，每条标注来源（Subagent 探查 / AI 自读 / 用户确认 / 文档）
   - 未覆盖的部分 → `<unverified_assumptions>`，标注"由执行阶段核实"
   - 用户裁决结果 → `<scope>` 的保留项 / 移除项

**报告本身不进共识包。** 用户看到的探查报告是过程材料；共识包只保留核实过的事实与用户裁决结果。

---

## 九、盲区处理

探查总有覆盖不到的地方。盲区必须显式处理，不能默认"没提到就是没问题"：

| 盲区情况 | 处理 |
|---------|------|
| 与本次需求无关 | 写进报告的"未覆盖"即可，不进共识包 |
| 与本次需求相关但没探到 | 进 `<unverified_assumptions>` + `<uncertainties>`，标注"由执行阶段核实" |
| 用户也无法确认 | 按 `./references/redesign-audit.md` 第六节，向执行阶段注入盘点兜底段落 |
| 探测结论与用户描述不符 | **停止**，向用户核对，不得顺着任一方往下写 |

盲区清单必须在探报告的第 4 节写明，不得省略——省略盲区等于把未知伪装成已知。

## 十、反模式

- ❌ 三个必要条件全过还硬派 Subagent（探测成了仪式）
- ❌ 全部维度都落在"自己读"却仍然派发
- ❌ 派发超过 4 个 Subagent
- ❌ 信息已经够了还凑满计划数量
- ❌ 不告知用户就派发
- ❌ 输入模板里不给位置线索，让 Subagent 全库乱翻
- ❌ 不给对照对象，只探主对象
- ❌ 让探查 Subagent 顺带给出改进建议或裁决
- ❌ 拿没有证据的条目当已核实事实写进 `<verified_facts>`
- ❌ 省略盲区，把未知写成已知
